## Phase 1 — Current State Audit (verified against the repo, not assumed)

### 1.1 Exactly how FreshFit currently works

`src/lib/freshFitScore.ts` exports one pure function,
`computeFreshFitScore(profile, job, dna)`, called with:

- `profile: MemberProfile` (from `member_profiles`)
- `job: ScrapedJob` (from `scraped_jobs`)
- `dna: { skills: CareerSkill[]; scope: CareerScope[] }` (from Forward
  DNA's `career_skills` / `career_scope` tables)

It sums six independent point buckets, capped at 100:

| Factor | Max pts | Logic |
|---|---|---|
| `skillsCoverage` | 50 | `profile.skills[]` (flat text array) vs. a hand-authored ~100-term `SKILL_KEYWORDS` dictionary found in the JD text |
| `roleRelevance` | 25 | Jaccard token overlap: JD title vs. `preferred_jobs[]` + past `employment_history[].title` |
| `locationFit` | 15 | Remote match, or job location string contains member's city, or `willing_to_relocate`, or neutral credit if no data |
| `keywordDensity` | 10 | Jaccard token overlap: `summary`+`headline`+`career_goals`+`strengths` vs. JD title+description |
| `dnaSkillEvidence` | 15 (bonus) | JD-detected skills that also exist in `career_skills`, weighted by evidence state (claimed 0.5 / demonstrated 0.8 / supported 1.0) |
| `scopeFit` | 10 (bonus) | Regex-detected "team of N" / "N direct reports" / "$X budget" in the JD, matched against the member's `career_scope` rows |

No LLM, no external API, 100% deterministic and already unit-tested
(`freshFitScore.test.ts`).

### 1.2 What inputs it currently uses

`MemberProfile` fields actually read: `skills`, `preferred_jobs`,
`employment_history`, `location`, `remote_preference`,
`willing_to_relocate`, `summary`, `headline`, `career_goals`,
`strengths`. `ScrapedJob` fields read: `title`, `description`,
`location`. Forward DNA: `career_skills`, `career_scope`.

**Fields that already exist on `MemberProfile` but FreshFit currently
ignores entirely:** `salary_min`, `salary_max`, `salary_currency`,
`max_commute_minutes`, `travel_willingness`, `schedule_preference`,
`work_style`, `preferred_industries`, `jobs_to_avoid`,
`preferred_benefits`, `target_role`, `target_timeframe`,
`weaknesses`/`jobs_not_enjoyed`/`motivators`/`biggest_challenge`. This
is the single biggest opportunity for FreshFit 2.0: several requested
dimensions (compensation, travel, some location nuance) need **zero new
member-facing data collection** — the data is already being collected
and simply isn't wired in.

### 1.3 Where scores are calculated

**Not client-side, not on page load.** `scripts/syncFreshFitScores.ts`
is a standalone Node script (service-role key, bypasses RLS) that
cross-joins every active member profile against every active
`scraped_job` row, calls `computeFreshFitScore`, and upserts rows
scoring `>= 35` into `job_matches`. Run via `npm run sync:freshfit`,
out-of-band (cron/manual), not per-request. The only *live* call site is
`submitMemberJob()` in `src/lib/opportunityEngine.ts`, used when a
member manually submits their own job lead — same function, same
result shape, computed synchronously in that one flow.

**This matters architecturally**: the dominant scoring path already has
zero latency budget pressure (it's an offline batch job), so FreshFit
2.0 has real room for more computation per pair without touching page
load times. The one live path (`submitMemberJob`) is a single
(member, job) pair, not a cross-join, so it can absorb more work too.

### 1.4 Where scores are persisted

`job_matches` table (`supabase/migrations/20260821000000_opportunity_engine.sql`):
`fresh_fit_score integer CHECK (BETWEEN 0 AND 100)`, `matched_skills
text[]`, `missing_skills text[]`, `score_breakdown jsonb DEFAULT '{}'`.
The jsonb column already has precedent for additive, backward-compatible
growth: `dnaSkillEvidence` and `scopeFit` were added to
`JobMatchScoreBreakdown` as optional (`?:`) fields after the table
existed, with zero migration and zero break to old rows. **The same
technique works for FreshFit 2.0** — no migration is required to store
a materially richer breakdown shape, because jsonb has no enforced
schema. (A *typed*, queryable hard-constraint column is a separate,
later, optional decision — see §5.6.)

### 1.5 Where FreshFit appears in the UI

| Surface | File | What it shows |
|---|---|---|
| Member Opportunity Engine | `OpportunityEnginePage.tsx`, `MatchCard.tsx` | `CircularProgress` ring (score only) + matched-skill pills, grouped into 3 presentation tiers via `getFreshFitTier` |
| Member Dashboard teaser | `OpportunityEngineTeaserCard.tsx` | Top single match's ring |
| Member empty state | `EmptyMatchesState.tsx` | Prose explaining what FreshFit means |
| Strategist Opportunity Engine | `StrategistOpportunityEnginePage.tsx` | Score badge + color, across all assigned members |
| Homepage hero (marketing, illustrative only) | `ForwardOSSnapshotCard.tsx`, `HeroFreshFitRing.tsx` | Hand-authored `82` / "Strong Match" sample — **not wired to real data anywhere**, purely marketing copy |
| Promoted `Opportunity.why_it_matches` | `buildWhyItMatches()` in `opportunityEngine.ts` | One templated sentence quoting the score + matched skills + a DNA-evidence-strength adjective |

Every real (non-marketing) surface shows **the number and a flat skill
list only** — exactly the gap the owner's brief describes. Nothing
today shows a per-factor breakdown, a hard-vs-soft distinction, or a
"what would improve this" action.

### 1.6 What data already exists that FreshFit 2.0 can reuse

- **Forward Score's pillar pattern** (`src/lib/forwardScore/`,
  `src/types/forwardScore.ts`) is the *exact* shape the owner is
  asking for, already shipped, already tested, already has a UI
  component (`PillarCard.tsx`): `{ key, label, score, weight,
  explanation, improvementLink }` per dimension, composite `total`,
  fixed-order array, deterministic pure functions, one `improvementLink`
  per pillar pointing at the page that would raise it. **FreshFit 2.0
  should reuse this exact shape and its UI conventions rather than
  invent a second pattern for the same concept in the same app.**
- **`STATE_WEIGHT`** (claimed/demonstrated/supported) is already shared
  between `freshFitScore`'s DNA bonus and Forward Score's Evidence
  Quality pillar — a single weighting scheme, not two. Continue that.
- **Career Compass's `readiness_scores.careerDirection`** (0-100) is
  already computed (`readinessEngine.ts`) and already reused by Forward
  Score's `goalAlignmentPillar` as-is, no rescaling. FreshFit 2.0's
  "does the role align with my career direction" dimension can read the
  identical field the identical way — zero new computation.
- **`career_scope` / `career_skills`** (Forward DNA) already flow into
  FreshFit today via `scoreSkillEvidence` / `scoreScopeFit` — this is
  the "Evidence Strength" dimension the owner is asking for; it exists,
  it just isn't broken out and explained as its own named thing today.
- **`parseScopeSignals()`'s regex-extraction technique** (team size /
  direct reports / budget from free text) is the established,
  already-approved pattern in this codebase for "pull a number out of a
  job description without an LLM." The same technique is the right tool
  for extracting a salary range out of `scraped_jobs.salary_text` (see
  §5.3) and is explicitly cited as prior art in the (approved but
  unbuilt) Career Vault spec.
- **`getFreshFitTier()`** (presentation-only, explicitly documented as
  *not* a validated scoring threshold) can be kept completely as-is —
  it operates on the final composite score regardless of how that score
  is now composed internally.

### 1.7 Which required inputs do NOT currently exist

| Requested capability (owner's brief) | Blocking gap |
|---|---|
| Seniority Alignment | No seniority/level field anywhere — not on `MemberProfile`, not on `ScrapedJob`. Would require either title-parsing heuristics (e.g. "Senior", "Director", "II/III") or a new structured field. Not present today. |
| Education / Certification Alignment (as a *requirement match*, not just "member has X") | `MemberProfile.education[]` / `.certifications[]` exist; `ScrapedJob` has no structured requirements field, only free-text `description`. Matching would require requirement-parsing out of free text, which does not exist today. |
| Work-authorization hard constraint | No field exists anywhere in this schema for work authorization status or requirement. |
| Structured job compensation | `ScrapedJob.salary_text` is free text only (e.g. `"$120K–$130K"` or `null`); there is no `salary_min`/`salary_max` on jobs the way there is on `MemberProfile`. A parser is required (see §5.3), and many postings will have no salary text at all. |
| Structured job work-arrangement | `Opportunity` (the strategist-curated table) has a `work_arrangement` column; `ScrapedJob` (FreshFit's actual input) does **not**. Today's `locationFit` infers remote-ness by checking whether the word "remote" appears in the free-text `location` field. |
| "Career Vault" as a literal upstream input | See §1.9 — Career Vault is an **approved but unbuilt** spec, not a live data source today. |

### 1.8 Architectural constraints that must be preserved

1. **FreshFit stays pure/deterministic.** No Supabase client, no I/O,
   no LLM call inside `computeFreshFitScore` or its callers in
   `freshFitScore.ts`/`matching.ts` — this is a hard, explicit,
   repeatedly-stated design rule in this codebase (see `freshFitScore.ts`'s
   own header comment and the Career Vault spec's confirmation that "no
   AI/LLM integration exists anywhere in `src/`").
2. **`fresh_fit_score` stays an integer 0-100** — enforced by a DB CHECK
   constraint; any redesign must still resolve to one such composite
   number for backward compatibility with the column, `getFreshFitTier`,
   and every UI ring/badge that renders it directly.
3. **`job_matches` is written only by service-role scripts** (plus the
   member's own `dismissed_at` and the strategist's own
   `promoted_opportunity_id`) — RLS has no authenticated INSERT policy.
   Any new write path must go through the same sync script or
   `submitMemberJob`, not a new client-side write.
4. **`score_breakdown` is jsonb** — grow it additively; do not assume or
   require a schema migration for the *shape* of the breakdown.
5. **`matched_skills` / `missing_skills` are real columns** other code
   already reads (`MatchCard.tsx`'s skill pills, `buildWhyItMatches()`).
   Keep populating them even as the richer per-dimension evidence lives
   alongside in `score_breakdown`.
6. **DI-friendly module pattern**: every Forward DNA / Opportunity
   Engine module takes `client: SupabaseClient = supabase` as its last
   param for unit-testability without a real connection. Any new
   FreshFit 2.0 data-access module should follow this, not the pure
   scoring functions themselves (which take no client at all — keep it
   that way).

### 1.9 Technical debt directly affecting this project

1. **Production score distribution is currently broken.**
   `opportunityEngineTiers.ts`'s own code comment states: *"a recent
   production run persisted zero matches at the real >=35
   scoring/persistence threshold."* Combined with `syncFreshFitScores.ts`
   permanently discarding (never writing) any pair scoring below 35,
   this means the current pipeline may currently be showing **most or
   all members zero Opportunity Engine matches in production**. This is
   a pre-existing bug, not something introduced by this redesign, but
   FreshFit 2.0 must not ship without deliberately addressing it (see
   §5.7) — a prettier breakdown on top of a score distribution that
   never persists anything doesn't fix the member-facing problem.
2. **`ScrapedJob` has no structured salary or work-arrangement fields**,
   forcing free-text inference for two of the requested new dimensions.
3. **The Homepage hero's FreshFit display is 100% hand-authored sample
   data**, disconnected from real scoring — not a defect to fix in this
   project (it's explicitly marketing-only, already reviewed/approved in
   a separate recent project), but worth naming so nobody mistakes it
   for a real integration point.
4. **`getFreshFitTier`'s thresholds (75/50) are explicitly documented as
   uncalibrated** — any redesign of the underlying score composition
   should treat these as provisional too, not sacred.

### 1.10 Which existing features must not regress

- `MatchCard.tsx`, `OpportunityEngineTeaserCard.tsx`,
  `StrategistOpportunityEnginePage.tsx`, `EmptyMatchesState.tsx` — all
  currently read `match.fresh_fit_score` and `match.matched_skills`
  directly; both must keep working unchanged for members/strategists on
  old cached data during rollout.
- `buildWhyItMatches()` — reads `score_breakdown.dnaSkillEvidence`
  directly; that key must keep being written (additively) even if it's
  now *also* represented inside a richer `dimensions[]` array.
- `getJobMatches`, `getJobMatchesForStrategist`, `dismissJobMatch`,
  `promoteMatchToOpportunity` — no interface changes needed or proposed.
- `computeFreshFitScore`'s existing test suite
  (`freshFitScore.test.ts`) encodes real behavioral contracts (e.g.
  "never exceeds 100," "unrelated job scores low") that any redesign
  must still satisfy, even if internal composition changes.
- The homepage hero's illustrative FreshFit display (out of scope,
  untouched, unrelated system).

condensed findings below, classified per the required rubric.

**Overall Phase 2 conclusion (HIGH CONFIDENCE):** nothing in the OSS
landscape clears the bar for adoption in V1. The strongest pattern found
in research — "deterministic requirement-by-requirement evidence
matching, embeddings only as an optional accuracy layer, LLM only as an
optional explanation polish, never as the source of truth" — is **already
exactly how this codebase's own Forward Score and FreshFit are built**.
V1 should continue building on the existing in-house, dependency-free,
fully-tested pattern rather than adopting an external library. This
also satisfies the license rule by construction: nothing new is being
depended on, so there is no GPL/AGPL exposure to analyze.

## Phase 3 — Self-Answered Design Questions

Each question: choices considered → recommendation → why → confidence →
what to revisit.

### Q1. What shape should a "dimension" take?

**Choices:** (a) invent a new FreshFit-specific shape; (b) reuse
`ForwardScorePillarResult` type directly; (c) define a new but
structurally identical `FreshFitDimensionResult` type.

**Recommendation: (c).** Structurally mirror
`ForwardScorePillarResult` (`key, label, score, weight, explanation,
improvementLink`) but as FreshFit's own type, plus two FreshFit-specific
additions Forward Score doesn't need: `evidence: string[]` (what backed
this score) and `gaps: string[]` (what's missing) — directly answering
the owner's "which parts of my evidence support this" and "where am I
weak" questions per-dimension, not just globally.

**Why:** Importing the literal Forward Score type would wrongly couple
two independent scoring systems (a job-fit score and a profile-readiness
score) that happen to share a good pattern, not a shared identity —
Forward Score's pillars are about *the member's profile in general*;
FreshFit's dimensions are about *this member against this one job*.
Copying the shape (not the type) keeps them decoupled while staying
visually/behaviorally consistent for the member.

**Confidence: HIGH.**
**Revisit if:** the owner wants these two systems formally unified into
one generic "scored dimension" type shared across the app — reasonable,
but a bigger refactor than this project's scope; defer.

### Q2. Should the top-line `fresh_fit_score` still be a single 0-100 number?

**Recommendation: Yes, keep it.** It's a DB CHECK constraint, and every
existing UI surface (`CircularProgress` rings, tier grouping, sort
order) is built around one comparable number. Explainability is
additive (new `dimensions[]`), not a replacement for the composite.

**Confidence: HIGH.** This is essentially forced by "preserve existing
functionality."

### Q3. Which dimensions ship in V1 vs. defer to V2?

See the full table in Phase 5. **Recommendation, briefly:** ship
Skills & Evidence, Role Relevance, Career Direction Alignment,
Compensation Alignment, Location/Remote/Commute/Travel Alignment — all
five are computable **today**, from data that already exists, using
techniques already proven in this codebase. Defer Seniority Alignment
and Education/Certification Alignment — both require net-new data or
requirement-parsing infrastructure this codebase doesn't have.

**Confidence: HIGH** on what's includable now; **MEDIUM** on exact
per-dimension point weights (see §5.2 — these are provisional and
should be validated against real score distributions before launch,
same caveat that already exists for `getFreshFitTier`'s thresholds).

### Q4. How should "hard constraints" work, given the owner's examples (work authorization, required location, salary floor, mandatory certification) mostly aren't backed by real data today?

**Recommendation:** Build the **hard-constraint framework** now (a
`hardConstraints: FreshFitHardConstraint[]` array with `status: 'met' |
'blocked' | 'unknown'`), but only **activate** constraints V1's data can
support *without risking false blocks on messy/missing free-text data*:

- **Compensation floor**: activate. `member_profiles.salary_min` already
  exists and is explicitly member-stated. When `scraped_jobs.salary_text`
  parses (see §5.3) to a confident range whose *maximum* is below the
  member's `salary_min`, mark `blocked`. When parsing fails or is
  absent, mark `unknown` — never `blocked` on missing data.
- **Remote-only mismatch**: activate, but conservatively. When
  `remote_preference === 'remote'` (an explicit member statement) AND
  the job's location text contains no remote signal AND doesn't match
  the member's city AND `willing_to_relocate` is false, mark `blocked`.
  Otherwise `unknown`/`met`.
- **Work authorization**: **do not activate** — no field exists
  anywhere in this schema. Framework supports it; V1 ships zero rows
  for this key. Flagged for the owner: adding a real
  `work_authorization` field to `member_profiles` (and, ideally, a
  matching signal on jobs) is a schema change, out of scope for this
  phase, and should be a deliberate V2 product decision, not smuggled
  in here.
- **Mandatory certification**: **do not activate** — job requirements
  aren't parsed at that granularity from free text yet. Same disposition
  as work authorization.

**Why not activate all four as asked:** hard-blocking hides an
opportunity from a member entirely. Given today's job-posting data is
free text scraped from Indeed (unreliable, incomplete, ToS-fragile per
the Opportunity Engine migration's own disclaimer), a false-positive
hard block is a worse failure mode than an over-generous soft flag. This
directly follows the codebase's own established philosophy, visible
throughout `freshFitScore.ts`: *"no signal = neutral credit,"* never
*"no signal = penalize."*

**Confidence: MEDIUM overall, HIGH on the "build the framework, activate
conservatively" principle, NEEDS OWNER REVIEW on the exact remote-only
activation rule** — this is a real behavior change (something can now be
visibly marked "blocked" that wasn't before) and deserves an explicit
yes before implementation, not just a provisional default.

### Q5. Does FreshFit 2.0 need semantic/embedding matching to be "explainable"?

**Recommendation: No, not for V1.** The owner's actual stated questions
("why is this an 82," "what am I missing," "is this worth pursuing")
are about **decomposing and narrating an existing score**, not about
*improving match accuracy* via better semantic understanding. These are
different problems. YAGNI: ship the explainability layer on the current
deterministic engine first; revisit embeddings only if, after shipping,
the deterministic dimensions themselves are found to be too coarse
(e.g., missing clear synonym matches like "JS" vs "JavaScript").

**Confidence: HIGH.**

### Q6. Should the "is this worth pursuing / what should I do next" answer come from an LLM?

**Recommendation: No — a deterministic rule engine, mirroring
`nextBestMove.ts`'s exact established pattern** (ordered rule checks
against computed values → one matched `{ key, headline, detail, cta }`
result, with a neutral fallback). A new, small,
FreshFit-scoped module (e.g. `src/lib/freshFitScore/recommendation.ts`)
applying rules like "if any hard constraint is blocked → 'Read the
details before applying'"; "if composite >= 75 and no blocked
constraints → 'Strong match — worth pursuing'"; "if 1-2 dimensions are
weak but nothing's blocked → 'Worth a look, but close X gap first'";
etc. Zero API calls, zero latency cost, fully unit-testable, consistent
with the codebase's one existing "recommend one action" precedent.

**Confidence: HIGH.**

### Q7. Does the "Career Vault" dependency in the owner's diagram exist to build against?

**Recommendation: No — and the diagram's shape needs a factual
correction, not a silent workaround.** Per the repo audit: Career Vault
has an **approved design spec**
(`docs/superpowers/specs/2026-09-01-career-vault-capability-engine-design.md`,
"Design direction approved 2026-09-01") but **zero implementation** —
no `career_wins` table, no migration, nothing beyond the doc. Critically,
that spec's own architecture makes Career Vault a **write-path into
Forward DNA's existing `career_skills.state`**, not a separate data
store FreshFit would need a new integration for. FreshFit already reads
`career_skills` today (`scoreSkillEvidence`). **Conclusion: FreshFit 2.0
needs zero new integration work for Career Vault.** The moment Career
Vault ships (a separate, already-spec'd project), every skill it
upgrades from `claimed` to `demonstrated`/`supported` automatically
improves that member's FreshFit Evidence Strength dimension, with no
FreshFit code change required — exactly the same "connect, zero changes
needed" relationship the Career Vault spec itself already documents for
this exact scoring function.

**Confidence: HIGH.**

### Q8. Is the owner's drawn pipeline (Compass ↓ DNA ↓ Vault ↓ Opportunity Engine ↓ FreshFit ↓ Applications...) accurate to the real architecture?

**Recommendation: Mostly, with two corrections worth stating plainly
rather than silently designing around:**

1. Career Compass and Forward DNA are **not** a strict pipeline today —
   they're sibling inputs that **fan in** to Forward Score (and, in this
   design, to FreshFit) independently. Forward DNA doesn't gain Career
   Compass data as a prerequisite; both are read directly by the
   consumer. FreshFit 2.0 should do the same: read `career_skills`/
   `career_scope` (Forward DNA) and `readiness_scores.careerDirection`
   (Career Compass) as two independent inputs, not a chained pipeline.
2. Opportunity Engine isn't strictly *upstream* of FreshFit — FreshFit
   is a library **called by** Opportunity Engine's sync script and
   `submitMemberJob`. It's a sub-component, not a separate pipeline
   stage after it. This stays true in FreshFit 2.0: same call sites,
   richer return shape.

Downstream (FreshFit → Applications / Resume Tailoring / Interview
Prep / ForwardOS) is directionally correct and already has one real,
live instance today: `buildWhyItMatches()` feeds FreshFit's output into
a promoted `Opportunity.why_it_matches` field. V1 should strengthen that
existing single connection (richer, per-dimension-aware copy) rather
than build new, unrequested "Resume Tailoring" or "Interview Prep"
consumer features — those are out of scope and not asked for yet.

**Confidence: HIGH** on the factual correction; **HIGH** on scope
(don't build new downstream consumers now).

### Q9. Typed columns vs. jsonb for the new breakdown shape?

**Recommendation:** Keep `score_breakdown jsonb` for V1's richer shape —
zero migration needed (see §1.4). If/when a *hard constraint* needs to
be efficiently queried/filtered at the SQL level (e.g., "show me only
non-blocked matches" as a `WHERE` clause instead of app-level
filtering), promote just that to a real typed column
(`is_hard_blocked boolean generated always as (...) stored`, or a
plain trigger-maintained column) as a small, separate, additive
migration in the *implementation* phase — not this one, and not unless
a real performance/filtering need shows up.

**Confidence: MEDIUM.** Reasonable default; genuinely a "wait and see"
call, not a strong opinion.

### Q10. Should V1 fix the "zero matches persisted in production" bug as part of this project?

**Recommendation: Yes, address it, but as a calibration/persistence
change, not a redesign of storage philosophy from scratch.**
Specifically: separate "compute and store" from "is this good enough to
show a member" — same separation `opportunityEngineTiers.ts` already
insists on for presentation tiers vs. the real threshold. Store every
computed (member, job) pair's dimensions and composite score
(or, if volume is a genuine concern, the top N per member regardless of
score) rather than silently discarding anything under a fixed cutoff.
Let the UI/presentation layer decide what's "worth showing." This is a
storage-policy change inside `syncFreshFitScores.ts`, not a schema
change, and directly serves the owner's stated goal (a member should be
able to see *why* something scored low, not have it vanish before they
ever see it).

**Confidence: HIGH** on the principle; **NEEDS OWNER REVIEW** on the
exact policy (store everything vs. top-N vs. a lowered-but-still-real
floor) — this has real storage/row-count and "how many low matches do
we want to show a member" product implications the owner should weigh
in on, not something to lock in unilaterally.

## Phase 4 — Architectural Approaches

### A. Enhanced deterministic / weighted heuristic engine

Extend `computeFreshFitScore` with more named, weighted dimensions
(same Jaccard/regex/dictionary techniques already in use), each
producing its own `{ score, explanation, evidence, gaps }`, composed
into the same 0-100 total.

| | |
|---|---|
| Explainability | **Excellent** — every point is traceable to a specific rule |
| Reliability | **Excellent** — same output for same input, forever |
| Token/API cost | **Zero** |
| Latency | **Negligible**, no change from today |
| Testability | **Excellent** — pure functions, same pattern as existing 100%-covered `freshFitScore.test.ts` |
| Maintainability | **High** — small, isolated, named functions, same shape as Forward Score's `pillars.ts` |
| Privacy | **Excellent** — no data leaves the process, ever |
| Data requirements | Uses only data that already exists |
| Operate without paid APIs at launch | **Yes, trivially** |
| Ability to improve later | Good — dimensions can be individually swapped for smarter logic later without touching the others |
| Compatibility with current architecture | **Perfect** — literally an extension of the existing file |

### B. Hybrid deterministic + semantic intelligence engine

Same as A, plus an optional semantic-similarity pass (embeddings) used
*only* to expand skill-matching (e.g. catch "JS" ≈ "JavaScript",
"IC" ≈ "individual contributor") as a secondary signal inside the
Skills dimension — never the primary score.

| | |
|---|---|
| Explainability | **Good** — deterministic dimensions stay fully explainable; the semantic layer needs its own "why" (similarity score + matched phrase), slightly harder to narrate simply |
| Reliability | **Good, not perfect** — embedding model/version pinning needed for reproducibility |
| Token/API cost | Low if self-hosted (e.g. `sentence-transformers`, no per-call API fee) but adds real compute/infra cost (model hosting, memory) |
| Latency | Fine offline (batch sync script); would need care if ever used live |
| Testability | Harder — similarity thresholds need calibration/golden-set tests, not pure assertions |
| Maintainability | Medium — one more moving part (model version, embedding cache) |
| Privacy | Good if self-hosted; bad if routed through a third-party embeddings API |
| Data requirements | Needs a corpus of text to embed — already have it (JD + profile text) |
| Operate without paid APIs at launch | **Yes, if self-hosted**; no if using a hosted embeddings API |
| Ability to improve later | **Very good** — this is the natural "V2 accuracy" lever |
| Compatibility with current architecture | Requires a new dependency + likely a background job for embedding caching; bigger lift than A |

### C. AI-heavy interpretation architecture

LLM reads the full JD + profile and generates the score, dimensions,
and explanation directly.

| | |
|---|---|
| Explainability | **Poor-to-fair** — LLM explanations *sound* plausible but aren't guaranteed to reflect the actual reasoning; classic hallucination/consistency risk |
| Reliability | **Poor** — same input can produce different scores across calls/model versions, directly violating this codebase's explicit deterministic-core principle |
| Token/API cost | **Real and recurring**, scales with (members × jobs) — expensive precisely because this pipeline is a cross-join, not a single lookup |
| Latency | Bad for the batch cross-join path; would force either huge batch cost or a redesign to score-on-demand only |
| Testability | **Poor** — cannot assert exact outputs; can only spot-check |
| Maintainability | Low — model/prompt drift risk over time |
| Privacy | Depends on vendor; sends member profile + job data to a third party unless self-hosted |
| Data requirements | None extra, but quality is prompt-sensitive |
| Operate without paid APIs at launch | **No** |
| Ability to improve later | High ceiling, but at the cost of everything above |
| Compatibility with current architecture | **Poor fit** — this codebase has zero AI/LLM dependencies anywhere today and an explicit, repeated design principle against nondeterministic core scoring |

### Recommendation: **Approach A for V1**, with Approach B's semantic layer explicitly named as the natural, opt-in V2 enhancement (never replacing A, only supplementing the Skills dimension). **Approach C is rejected outright** for the core score, consistent with the owner's stated strong preference, this codebase's existing zero-AI footprint, and the batch-cross-join cost profile making per-call LLM pricing genuinely prohibitive at scale (member count × active job count, recomputed on every sync run).

**Confidence: HIGH.**

## Phase 5 — FreshFit 2.0 Dimension Model

### 5.1 Shape

```ts
export type FreshFitDimensionKey =
  | 'skillsEvidence'      // merges today's skillsCoverage + dnaSkillEvidence + scopeFit
  | 'roleRelevance'       // today's roleRelevance, renamed/explained
  | 'careerDirection'     // NEW — reuses Career Compass's readiness_scores.careerDirection
  | 'compensation'        // NEW — profile salary_min/max vs. parsed job salary_text
  | 'locationAndLogistics' // UPGRADE of today's locationFit — folds in max_commute_minutes, travel_willingness, willing_to_relocate

export interface FreshFitDimensionResult {
  key: FreshFitDimensionKey
  label: string
  score: number                 // 0-100, this dimension only
  weight: number                 // 0-1, sums to 1 across all dimensions
  status: 'strong' | 'moderate' | 'weak' | 'no-data'
  explanation: string             // plain-language, same style as ForwardScore pillars
  evidence: string[]               // what backed this score (matched skills, scope, etc.)
  gaps: string[]                    // what's missing / would raise this
  improvementLink: { label: string; to: string } | null
}

export interface FreshFitHardConstraint {
  key: 'compensationFloor' | 'remoteRequirement' | 'workAuthorization' | 'requiredCertification'
  label: string
  status: 'met' | 'blocked' | 'unknown'
  reason: string
}

export interface FreshFitRecommendation {
  key: 'strong_pursue' | 'worth_a_look' | 'close_the_gap_first' | 'read_details_first' | 'likely_not_a_fit'
  headline: string
  detail: string
}

export interface FreshFitResult {
  score: number                          // unchanged: 0-100 composite, same DB column
  dimensions: FreshFitDimensionResult[]    // NEW
  hardConstraints: FreshFitHardConstraint[] // NEW
  recommendation: FreshFitRecommendation     // NEW
  matchedSkills: string[]                     // UNCHANGED shape, still populated
  missingSkills: string[]                      // UNCHANGED shape, still populated
  breakdown: JobMatchScoreBreakdown              // UNCHANGED legacy flat shape, still populated additively
}
```

`score_breakdown` (jsonb) stores both `breakdown` (legacy, unchanged
keys, for `buildWhyItMatches()` and any other existing reader) and the
new `dimensions`/`hardConstraints`/`recommendation` — fully additive,
zero migration, zero regression risk (§1.4, §1.10).

### 5.2 V1 dimensions, weights, and data sources

| Dimension | Provisional weight | Data source (all exist today) |
|---|---|---|
| Skills & Evidence | 40 | `profile.skills[]` + `SKILL_KEYWORDS` dictionary (existing) + `career_skills` state weighting (existing) + `career_scope` regex bonus (existing) — unified into one explainable dimension instead of three separate score buckets |
| Role Relevance | 20 | `preferred_jobs[]` + `employment_history[].title` vs. JD title (existing Jaccard logic, unchanged) |
| Career Direction Alignment | 15 | `career_compass` `readiness_scores.careerDirection`, read the same way `goalAlignmentPillar` already does. If the member has never taken Career Compass, `status: 'no-data'`, dimension excluded from the weighted total (re-normalize remaining weights) rather than penalized — mirrors the existing "no signal = neutral" philosophy |
| Compensation Alignment | 15 | `profile.salary_min`/`salary_max` vs. parsed `job.salary_text` (see §5.3). `no-data` when the JD has no parseable salary — never penalized |
| Location & Logistics | 10 | `remote_preference`, `willing_to_relocate`, `max_commute_minutes`, `travel_willingness` vs. job location text — an upgrade of today's `locationFit`, same neutral-on-missing-data philosophy |

Weights are **provisional (MEDIUM CONFIDENCE)** — they preserve
Skills' current dominance (roughly the same 50-of-100 share it has
today) while giving the three new signals real but secondary weight.
These must be validated against real score distributions in the
implementation phase (see §5.7) before being treated as final.

### 5.3 Compensation parsing (new, small, in-house — no dependency)

A `parseSalaryRange(salaryText: string | null): { min: number; max: number } | null`
helper, same technique/confidence level as `matching.ts`'s existing
`BUDGET_RE`/`parseScopeSignals` (regex for `$X-$Y`, `$Xk`, `$X/hr` with
a hint of employment-type-aware hourly-to-annual conversion). Unparseable
or absent text → `null` → dimension/constraint reports `no-data`, never
a false negative.

### 5.4 Location upgrade

Today's binary "remote match / city substring match / relocate flag /
neutral" gets three additions, all from data already on `MemberProfile`:
`max_commute_minutes` (soft credit if job location is same metro and
commute is plausible — best-effort, not GPS-precise), `travel_willingness`
(soft signal if JD mentions travel-percentage language, reusing the
"detect a number/phrase in free text" technique), all folded into one
explainable dimension rather than spread across the model.

### 5.5 V2 (explicitly deferred, YAGNI)

| Deferred dimension | Why deferred |
|---|---|
| Seniority Alignment | No seniority field exists on either side; needs new inference or new data — real scope, not a quick add |
| Education / Certification Alignment (requirement-level) | `ScrapedJob` has no structured requirements; needs JD requirement-parsing infrastructure that doesn't exist |
| Semantic/embedding skill expansion | Approach B territory — real value, real infra cost, not needed to satisfy the stated explainability goal |
| O*NET/ESCO occupation normalization | Real value for title/skill quality long-term; a multi-week data-ingestion project on its own, unjustified by this project's actual ask |
| Preferences Alignment as its own dimension (`jobs_to_avoid`, `preferred_industries`, `preferred_benefits`, `schedule_preference`, `work_style`) | Real data exists, genuinely could be V1.1 — deferred only because the owner's explicit dimension list didn't prioritize it and five dimensions is already a meaningful, shippable step up from one number |

### 5.6 Hard constraints (see Q4 for full reasoning)

V1 activates exactly two: **Compensation Floor** and **Remote
Requirement Mismatch**, both `unknown`-safe on missing/ambiguous data,
never silently hiding a match — a blocked constraint is *shown*
prominently (with its reason), not used to delete the match from view.
Work authorization and mandatory certification exist in the type but
ship with zero active rows in V1, clearly flagged to the owner as
needing either new data collection or JD requirement-parsing before
they can be responsibly activated.

### 5.7 Fixing the zero-persisted-matches bug (§1.9, Q10)

Recommended (NEEDS OWNER REVIEW on exact policy, see Q10): change
`syncFreshFitScores.ts`'s storage policy from "discard anything under
35" to "store every computed pair" (or, if row-count is a real concern,
"store the top N per member regardless of score"), and let
`getFreshFitTier`/UI decide what a member sees by default. This makes
the "why is this a 40, not an 80" question answerable for matches that
are currently invisible entirely, and gives the team real distribution
data to calibrate `getFreshFitTier`'s thresholds against for the first
time.

### 5.8 UI implications (naming only — no implementation in this phase)

A new `FreshFitBreakdownCard` (or expanded `MatchCard`) would render
`dimensions[]` the same way `PillarCard.tsx` already renders Forward
Score pillars — same visual language, same "score + explanation +
improvement link" card, so a member sees one consistent mental model for
"a score with a reason" across Forward Score and FreshFit rather than
two different UI languages for the same concept. `hardConstraints`
render as a distinct, more prominent flagged-warning treatment (not a
regular dimension card) when `status === 'blocked'`. This is a UI/UX
design decision for the *implementation* plan, named here only to
confirm the data shape supports it cleanly.
