# FreshFit 2.0 — Owner Review

**Branch:** `freshfit-2` (based on `origin/main`, NOT merged — awaiting your review/approval)
**Status:** Implementation complete. Typecheck clean, production build clean, 369/369 tests passing (67 test files) excluding two stale sibling git worktrees with an unrelated, pre-existing environment issue (see "Known non-issues" below).

## What changed, in one paragraph

FreshFit went from an opaque 0-100 heuristic score into explainable job-fit
intelligence: five weighted, independently-tested dimensions (Skills &
Evidence, Role Relevance, Career Direction Alignment, Compensation
Alignment, Location & Logistics), each carrying its own score, status,
evidence, confirmed gaps, and — critically — a separate **unknowns**
bucket so "we don't have enough data" is never silently treated as "you
don't qualify." Two hard constraints (compensation floor, remote-only
mismatch) surface prominently instead of being buried in a score. A
deterministic recommendation (`strong_pursue` / `worth_a_look` /
`close_the_gap_first` / `read_details_first` / `likely_not_a_fit`) and a
confidence rating (`high`/`medium`/`low`, based on how much real data
backed the score) round out the result. Everything is still 100% pure,
deterministic TypeScript — no LLM, no external API, no new paid
dependency, per your explicit instruction.

Separately, `scripts/syncFreshFitScores.ts` replaced its single hard
`MIN_SCORE_TO_STORE = 35` cutoff with a real ranking/persistence policy:
score every active member × active job pair, keep anything above a low
noise floor (20), persist each member's Top 25 (re-ranked fresh every
run, rank itself is never stored), and prune only this engine's own
untouched rows that fell out of the Top N — a member's dismissed matches,
strategist-promoted matches, and any legacy `engine_version = 1` row are
never touched by pruning.

## Architecture

`src/lib/freshFitScore.ts` (one 250-line file) became
`src/lib/freshFitScore/` (11 focused modules, each independently unit
tested):

| File | Responsibility |
|---|---|
| `types.ts` | Shared result/evidence/dimension/constraint types |
| `skillMatching.ts` | Exact / alias / transferable skill classification, scope-fit bonus |
| `roleRelevance.ts` | JD title vs. preferred titles + work history (jaccard) |
| `careerDirection.ts` | Passes through Career Compass's `readiness_scores.careerDirection` |
| `compensation.ts` | Salary-range parsing + compensation dimension + hard constraint |
| `location.ts` | Remote/location/relocation/travel dimension + hard constraint |
| `confidence.ts` | High/medium/low based on how many dimensions had real data |
| `recommendation.ts` | Deterministic rule table (mirrors `forwardScore/nextBestMove.ts`) |
| `tiers.ts` | Strong/Good/Fair/Weak thresholds + shared badge styles |
| `jobMatchPersistence.ts` | Pure ranking/pruning policy for the sync script |
| `score.ts` | Orchestrator: composes the above into one `FreshFitResult` |

`src/lib/freshFitScore.ts` (the old filename) is now a **1-line re-export
shim** pointing at the new folder — see "Known limitation" below for why
it couldn't simply be deleted.

New UI: `src/components/freshFit/FreshFitBadge.tsx` (shared score badge,
replaces two independently-drifting inline `scoreColor()` functions) and
`FreshFitDetails.tsx` (expandable "Why this score?" panel — dimension
evidence/gaps/unknowns, hard-constraint warnings, recommendation). Both
wired into `OpportunityEnginePage.tsx` (member) and
`StrategistOpportunityEnginePage.tsx` (strategist).

## Data model

One additive migration:
`supabase/migrations/20260905000000_freshfit_engine_v2.sql` adds
`job_matches.engine_version integer NOT NULL DEFAULT 1` (pre-existing
rows stay `1`, untouched) plus a supporting index. **No other schema
changes** — the richer v2 payload (dimensions, hard constraints,
confidence, tier, recommendation, unknowns) lives inside the existing
`score_breakdown jsonb` column under a new `v2` key
(`src/lib/freshFitScore/score.ts::toScoreBreakdownPayload`). Legacy flat
fields (`skillsCoverage`, `roleRelevance`, `locationFit`, `keywordDensity`,
`dnaSkillEvidence`, `scopeFit`) are still populated on every match for
any code that hasn't been updated to read `v2`.

## Deliberate design decisions worth your attention

1. **Evidence tier no longer moves the score directly once a skill is a
   confirmed exact/alias match.** A flat, self-reported skill and a
   Forward-DNA-`supported` skill both count as `confirmed_match` at the
   dimension-score level — evidence *quality* is Forward Score's
   Evidence Quality pillar's job, not FreshFit's. `dnaSkillEvidence`
   still increases in the legacy breakdown field, so nothing regresses
   for old readers; one pre-existing test assertion
   (`freshFitScore.test.ts`) was updated from `toBeGreaterThan` to
   `toBeGreaterThanOrEqual` to reflect this intentionally changed
   contract (documented inline in that test).
2. **`SPARSE_PROFILE_THRESHOLD = 1`** (in `skillMatching.ts`): a member
   is only "too sparse to call a gap" when they have **zero** skills on
   record anywhere (flat + Forward DNA). Any skill data at all is enough
   to call an undetected JD skill a confirmed gap rather than unknown.
   This was tuned during implementation — an initial threshold of 3
   caused a genuinely unrelated job (nursing vs. a welding-only profile)
   to score misleadingly high, because "insufficient evidence" was being
   applied too liberally. Worth revisiting with real production data.
3. **Dimension weights** (Skills & Evidence 0.40, Role Relevance 0.20,
   Career Direction 0.15, Compensation 0.15, Location 0.10) are carried
   over from the design spec as provisional/medium-confidence — flagged
   there and here for validation against real score distributions once
   this ships.
4. **Tier thresholds** (Strong ≥80, Good ≥60, Fair ≥40, Weak <40) were
   corrected during implementation to actually match your stated
   examples (82→Strong, 74/63→Good, 51/42→Fair, 31→Weak); the first
   draft's Fair floor (45) misclassified 42.

## Test coverage added

108 new/updated tests across 12 new test files (`types` has no test
file, it's pure interfaces) plus a rewritten `jobMatchPersistence.test.ts`
(13 tests: ranking, noise floor, persistence-below-old-cutoff, empty
input, pruning untouched/dismissed/promoted/legacy rows, mixed batch,
and 3 explicit privacy/member-isolation tests). Every scoring dimension,
the compensation/location hard constraints, confidence, recommendation,
tiers, seniority inference, and the full orchestrator (including every
pre-existing regression case ported forward) have dedicated unit tests.
New `FreshFitBadge`/`FreshFitDetails` component tests cover the UI layer.

A second pass added the three capability categories you explicitly asked
for that weren't yet covered: **seniority mismatch**, **overqualification**,
and **career-change** signal detection, plus explicit **privacy** tests.
Rather than bolt on a 6th scoring dimension (which would have meant
rebalancing all 5 existing weights and risked destabilizing an
already-shipped design), these were folded into the existing Role
Relevance dimension via a new `src/lib/freshFitScore/seniority.ts`
module:
- A JD implying 2+ seniority rungs above the member's current level
  (inferred from their most recent/current employment title) is a
  confirmed gap and knocks the score down (×0.7) -- title-based
  inference is best-effort, not certain, so this is a real signal, not
  a hard veto.
- The reverse (member looks 2+ rungs more senior than the role) is
  **never a score penalty** -- just an honest explanation note, since
  being overqualified doesn't mean you can't do the job.
- A deliberate career changer (preferred-jobs similarity high, but
  work-history similarity low) now gets scored against whichever of the
  two is the better match (`max()`, not a combined bag-of-words average)
  and gets positively-framed copy ("matches the direction you're
  pursuing, even though it differs from your recent work history")
  instead of being quietly penalized for not yet having done the work.

Privacy tests live in `jobMatchPersistence.test.ts`: both
`selectMatchesToPersist` and `selectStaleMatchesToPrune` are proven to
never return an id that wasn't present in their own input (no
fabrication/leakage), and a mixed-member scenario confirms one member's
row is judged strictly against the keep-set it was actually given, never
accidentally kept because another member's job id happened to be in a
different set. Per-member privacy is enforced by construction: neither
function has any concept of "member" at all, which is documented inline
as the reason this is safe to call in a shared loop.

## What was intentionally NOT done (YAGNI / explicitly out of scope)

- No semantic embeddings, no O*NET/ESCO taxonomy ingestion, no paid
  API — confirmed via the earlier OSS/licensing research phase that
  none of this is needed for a correct, explainable V1.
- No Career Vault wiring beyond what already exists — FreshFit already
  reads `career_skills`, and Career Vault's design has it write to that
  same table, so no new integration point was needed (per the earlier
  audit finding that Career Vault itself isn't implemented yet).
- No Seniority or Education/Certification dimensions — deferred per the
  original spec because `ScrapedJob` doesn't have structured fields for
  either yet.
- No merge to `main`. This branch is ready for your review only.
