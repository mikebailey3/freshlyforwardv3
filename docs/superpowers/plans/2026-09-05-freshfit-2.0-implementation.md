# FreshFit 2.0 Implementation Plan

> Executed inline, same session, by the same agent that wrote the spec —
> not handed off cold, so this plan documents file structure, interfaces,
> and task sequence (per writing-plans) without the full subagent-handoff
> step-by-step ceremony, which exists to brief a zero-context engineer.
> TDD discipline still applies to every module below.

**Goal:** Evolve FreshFit from one opaque score into explainable,
multi-dimension job-fit intelligence, fix the zero-persisted-matches bug
with an intelligent Top-N/noise-floor ranking policy, and surface it in
the Opportunity Engine UI — without breaking Forward Score, Forward DNA,
Search Readiness, or Career Vault privacy.

**Architecture:** Hybrid deterministic engine (Phase 4 Approach A from
the spec) — decompose `freshFitScore.ts` into focused modules under
`src/lib/freshFitScore/`, each pure and independently testable, composed
by one orchestrator. No AI/LLM in the scoring path.

**Spec:** `docs/superpowers/specs/2026-09-05-freshfit-2.0-explainable-scoring-design.md`
(and the owner's follow-up message expanding it — ranking policy,
evidence-status vocabulary, module decomposition — both are binding).

## Global Constraints

- `fresh_fit_score` stays an integer 0-100 (DB CHECK constraint unchanged).
- `score_breakdown` stays jsonb; grow additively, keep legacy flat keys.
- No client-side writes to `job_matches` beyond existing
  `dismissed_at`/`promoted_opportunity_id` policies — new writes go
  through `syncFreshFitScores.ts` (service role) or `submitMemberJob`.
- No LLM/embedding calls in the scoring path.
- `SKILL_KEYWORDS` must remain importable from `@/lib/freshFitScore`
  (consumed by `src/lib/linkedinOptimizer.ts`).
- Forward Score, Search Readiness, Career Vault: read-only reuse, zero
  behavior changes.
- Additive migration only; preserve historical rows via
  `engine_version`.

## Key Interfaces (locked before implementation)

```ts
// src/lib/freshFitScore/types.ts
export type EvidenceStatus =
  | 'confirmed_match' | 'likely_transferable' | 'unknown'
  | 'confirmed_gap' | 'hard_blocker'

export type FreshFitDimensionKey =
  | 'skillsEvidence' | 'roleRelevance' | 'careerDirection'
  | 'compensation' | 'locationAndLogistics'

export interface FreshFitDimensionResult {
  key: FreshFitDimensionKey
  label: string
  score: number
  weight: number
  status: 'strong' | 'moderate' | 'weak' | 'no-data'
  explanation: string
  evidence: string[]
  gaps: string[]
  improvementLink: { label: string; to: string } | null
}

export interface FreshFitHardConstraint {
  key: 'compensationFloor' | 'remoteRequirement'
  label: string
  status: EvidenceStatus   // 'confirmed_match' | 'hard_blocker' | 'unknown'
  reason: string
}

export type FreshFitConfidence = 'high' | 'medium' | 'low'

export type FreshFitTier = 'strong' | 'good' | 'fair' | 'weak'

export type FreshFitRecommendationKey =
  | 'strong_pursue' | 'worth_a_look' | 'close_the_gap_first'
  | 'read_details_first' | 'likely_not_a_fit'

export interface FreshFitRecommendation {
  key: FreshFitRecommendationKey
  headline: string
  detail: string
}

export interface FreshFitResult {
  score: number
  tier: FreshFitTier
  confidence: FreshFitConfidence
  dimensions: FreshFitDimensionResult[]
  hardConstraints: FreshFitHardConstraint[]
  recommendation: FreshFitRecommendation
  matchedSkills: string[]
  missingSkills: string[]
  breakdown: JobMatchScoreBreakdown   // legacy flat shape, unchanged
}
```

`computeFreshFitScore(profile, job, dna)` keeps its exact existing
signature (`profile: MemberProfile, job: ScrapedJob, dna: { skills,
scope }`) plus one new optional 4th param `careerDirectionScore: number
| null = null` — additive, every existing call site keeps compiling
without changes; the sync script and `submitMemberJob` are updated to
pass the real value.

## Persistence/Ranking Policy (locked, documented here for the executor)

- `NOISE_FLOOR = 20` — below this, a pair is true noise (essentially
  every dimension weak/no-data); never persisted regardless of rank.
- `TOP_N_PER_MEMBER = 25` — generous enough that "your best available
  opportunities" always has real content to show even in a thin job
  pool, bounded enough to cap `job_matches` growth per member
  (25 members-worth of rows is a small, predictable ceiling vs. the old
  unbounded-by-score-only approach).
- Rank is **not** a persisted column — it's `ORDER BY fresh_fit_score
  DESC` at query time (already what `getJobMatches`/
  `getJobMatchesForStrategist` do). Avoids a second source of truth that
  could go stale between sync runs.
- Pruning: after computing a member's new Top-N set, delete their
  existing `job_matches` rows where `engine_version = 2 AND
  scraped_job_id NOT IN (new set) AND dismissed_at IS NULL AND
  promoted_opportunity_id IS NULL`. Dismissed/promoted rows are never
  touched — they're the member's/strategist's own action history.
  `engine_version = 1` legacy rows are also never touched by this
  prune (only v2 runs manage v2 rows).
- Tier is derived from score at read time (`tiers.ts`), never persisted
  — cheap, pure, and can't go stale relative to the score.
